# The cyber package

The standard lists every control. Which of them an image must inspect follows
from what that image does. Where each one is applied, and what is left open,
is a person's work: the **cyber package** is where that work is written down.

The [reference web server's package](../examples/reference-web-server/package/README.md)
is the worked example.

## What is generated, and what is not

| | Who writes it | What it says |
| --- | --- | --- |
| [Controls, all of them](../examples/reference-web-server/INSPECTION-LIST.md) | Generated | Which controls this image inspects, which it inherits, and which have nothing here to apply to |
| [Control statements](../examples/reference-web-server/CONTROL-STATEMENTS.md) | Generated, from decisions a person wrote | What carries each control, and who carries the rest |
| [The package](../examples/reference-web-server/package/README.md) | **A person** | The architecture, the boundaries, where controls are applied, what is open, and what none of it claims |
| Diagrams | Generated from a description a person writes | The same architecture, drawn |
| The conformance score | Generated from evidence | What is actually evidenced, and how well |

Nothing about the package can be automated except its form. A check can say
that every section is present, that every capability is discussed, that every
diagram is referenced, and that nothing flagged elsewhere has been left out. It
cannot say whether the architecture is described correctly, or whether a
control really is applied where the package says it is. That is review.

## What decides the list of controls

An image declares **capabilities** in its hardening profile: what it does, in
the terms the standard's [inspection map](../artifacts/inspection-map.json)
uses. Each capability brings controls onto the list.

```json
"capabilities": ["serves-http", "terminates-tls"]
```

Declaring `terminates-mutual-tls` adds identification and access enforcement,
because verifying a client certificate is authentication. Removing it takes
them away again. That is the point: **the list of controls follows the image,
and changes when the image does.**

A capability can also raise a control the High baseline does not select, such
as output filtering for an image that renders content a caller supplied. Those
are not required. They are put in front of whoever inspects, to select or to
decline with a reason in the package.

The inspection list also flags a control whose answer looks wrong beside a
declared capability: one answered not-applicable that a capability says the
image does. The package must name each flagged control, so a flag cannot be
passed over in silence.

## What a package contains

Eight sections, in this order. The check requires each; what goes in them is
yours.

1. **What this image is.** What it does, in a paragraph, and every capability
   it declares, with what each brings. Say what it does *not* do: those are the
   controls that will appear the day someone adds a feature.
2. **Architecture.** The image as deployed: the security context it runs
   under, what is mounted, what listens, who the processes are. Drawn, not only
   described.
3. **Data flow and trust boundaries.** What crosses which boundary, in which
   direction, and what never crosses. Boundaries are the part a reader cannot
   infer: say where something stops being trusted.
4. **Where the controls are applied.** Which part of the image carries which
   control, and what the platform, host, and organization carry. State plainly
   that meeting the image's part does not satisfy a control: controls and
   criteria are many to many, and a control is satisfied only when every part
   of it is.
5. **Controls.** A pointer to the full list, the counts in each group, every
   flagged control, and every control raised as worth considering, with the
   decision taken on it.
6. **Evidence.** What the image evidences, and where the score is. The package
   is not evidence, and should say so.
7. **Deviations and what is open.** Every deviation, with its owner and expiry,
   and every control deliberately left open.
8. **What this package does not claim.** An authorization, an assessment, a
   STIG result, or a template for a different shape of image.

## Diagrams

One diagram cannot carry an architecture. The reference image's package draws
eight, generated by
[`build-package-diagrams.py`](../examples/reference-web-server/scripts/build-package-diagrams.py)
from [`scripts/svg.py`](../scripts/svg.py), which an adopting image copies:

| Kind | What it answers |
| --- | --- |
| Context | What surrounds the image, and what crosses the platform boundary |
| Data flow | What moves, where it rests, and what never leaves |
| Sequence, one per path that matters | What happens in order, and where each control acts |
| Lifecycle | How it starts, is judged healthy, stops, and where it fails closed instead |
| Deployment | What the platform gives it, and what it may write |
| Network | What listens, what it reaches, and who decides who may reach it |
| Identity and privilege | Who the processes are, and what they cannot do |

Generating them from a description keeps them in step with the image: a
diagram that is drawn by hand goes stale the first time the image changes, and
nothing says so. Run the generator with `--check` in CI.

## Checking the form

```sh
python ../container-hardening/scripts/check-package.py \
    --package package/README.md --profile hardening-profile.json \
    --inspection-list INSPECTION-LIST.md --statements CONTROL-STATEMENTS.md
```

It reports a missing section, a capability the package never discusses, a
diagram nobody references, a broken link, a flagged control the package does
not name, a placeholder left behind, and unreviewed decisions the package does
not admit to. A package that passes is well formed. Whether it is true is what
review decides.
